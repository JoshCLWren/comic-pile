# Issue #627: Remove reviews from the backend

## Objective

Remove the obsolete Reviews backend surface without affecting ratings, sessions, or historical reading activity. The implementation must make an explicit data-retention decision before any destructive migration is deployed.

## Current boundary to inspect

Before implementation, inventory every production and test reference matching `review`, `Review`, `/reviews`, and review-table foreign keys across:

- `app/api/` router registration and handlers;
- `app/models/` SQLAlchemy models and relationships;
- `app/schemas/` request and response models;
- `app/services/` and repository helpers;
- `alembic/versions/` creation, alteration, and foreign-key history;
- `tests/`, `tests_e2e/`, fixtures, factories, and seed scripts;
- OpenAPI snapshots, generated documentation, changelog entries, and active architecture docs.

The inventory must distinguish obsolete Reviews from ordinary numeric ratings and rating/session snapshots. Names containing `rating`, `rate`, `last_rating`, or session-event rating metadata are retained unless they are proven to exist solely for Reviews.

## Data-retention decision

Use a forward-only migration. Do not edit or delete historical Alembic revisions that may already exist in deployed databases.

The implementation PR must choose and document one of these deployment-safe options after inspecting production expectations:

1. **Drop immediately:** add a new migration that drops review foreign keys, indexes, and the review table. Use only when existing review rows have no retention value.
2. **Archive then drop:** export review rows to an explicitly named archival table or documented external artifact, verify row counts, then remove the production table in a later independently deployable migration.
3. **Retain table temporarily:** remove all application routes and model usage first, leave the orphaned table for one release, then drop it in a follow-up migration after production verification.

Default to option 3 when repository evidence does not establish that destructive deletion is safe. The issue must not be closed until the final persistence decision is implemented and documented.

## Implementation stages

### Stage 1: inventory and contract lock

- Record all review routes, schemas, models, services, fixtures, tests, migration objects, documentation references, and router registrations.
- Add a focused regression proving the retained OpenAPI contract contains no review operation while rating/session operations remain present.
- Confirm the frontend has no review calls before removing backend compatibility.

This stage is independently revertible and must not alter persisted data.

### Stage 2: remove runtime application support

- Remove review router registration and handlers.
- Remove review schemas, service/repository functions, authorization branches, and serializers.
- Remove review model relationships only after checking whether cascade settings affect retained entities.
- Delete review-only fixtures and rewrite tests that accidentally use Reviews to set up rating/session behavior.
- Preserve rating endpoints, `last_rating`, session events, undo snapshots, and reading history behavior.

Add negative API coverage confirming review endpoints return the intended unsupported response, normally 404 from absent routing, while authenticated rating and session endpoints retain their existing ownership behavior.

### Stage 3: persistence cleanup

- Add a new Alembic revision for the selected retention option.
- Drop dependent constraints and indexes before dropping columns or tables.
- Verify upgrade from the previous deployed head and migration from an empty database.
- If using a staged orphan-table release, create a follow-up issue and leave the parent open until the drop migration lands.

Never rewrite migration history to make the schema appear as though Reviews never existed.

### Stage 4: documentation and residue scan

- Remove Reviews from active API and architecture documentation.
- Keep historical changelog references when they describe past releases, but mark the feature removed where ambiguity would imply current support.
- Run a repository-wide residue check and classify every surviving `review` match. Generic code-review and pull-request-review wording is not product Reviews residue.

## Risks and containment

- **Ratings removed accidentally:** protect with focused rate/session API tests and explicit residue classification.
- **Cascade deletes:** inspect every foreign key and SQLAlchemy cascade before model removal.
- **Broken deployed upgrades:** use a new forward migration and test upgrade from the prior head.
- **OpenAPI drift:** assert review operations are absent and retained operations remain.
- **Hidden seed dependency:** run seed/setup paths after deleting review fixtures.
- **Irreversible data loss:** default to a staged orphan-table release unless deletion authorization is supported by repository or product evidence.

## Schema and contract impact

- Database migration: required for final persistence removal.
- API schema change: required, review operations disappear from OpenAPI.
- Authorization: review-specific ownership checks are removed; retained ownership checks must remain unchanged.
- Frontend/backend contract: no retained frontend contract should change because the frontend no longer calls Reviews.

## Regression coverage

At minimum, add tests proving:

- review routes are absent;
- review schemas and model imports are absent from runtime modules;
- rating submission and retrieval remain functional;
- session history still serializes rating metadata;
- undo or snapshot restoration involving ratings remains functional;
- ownership isolation for retained rating/session paths is unchanged;
- migration upgrade succeeds from the previous head;
- a fresh migration reaches one Alembic head;
- OpenAPI exposes no review operations;
- seed and fixture setup succeeds without Reviews.
