# Issue #3068: SEO - eliminate redirect chains, soft 404s, and orphaned public pages

## Problem

Crawlers and users should have one obvious canonical path to public content. Redirect chains, client-only soft 404s, and unreachable pages waste crawl effort and make the public surface harder to understand.

## Scope

- Inventory public routes and aliases
- Collapse redirects so legacy/alternate URLs reach the canonical URL in at most one redirect
- Make missing public routes return a real 404 response where the deployment stack permits it
- Ensure every indexable page is reachable from a meaningful internal link and/or the sitemap
- Remove obsolete public route aliases when safe
- Keep SPA fallback behavior only where the authenticated client application actually needs it

## Acceptance Criteria

1. No known public URL requires more than one redirect to reach its canonical destination
2. Missing public pages do not resolve as indexable soft-404 200 responses
3. Every indexable public route has at least one intentional discovery path from another public page or the sitemap
4. Canonical links and redirects agree on the same final URL
5. Tests cover representative canonical, redirected, missing, and authenticated deep-link cases

## Implementation Plan

### Phase 1: Audit Current Public Routes

1. **Inventory all public routes** in frontend routing configuration
   - Check `frontend/src/App.tsx` and `frontend/src/router.tsx`
   - Identify routes with redirects or aliases
   - Document current redirect chains

2. **Check for soft 404s**
   - Search for routes that return 200 status but show "not found" content
   - Check client-side routing that might silently fail

3. **Identify orphaned routes**
   - Check if all indexable routes are linked from sitemap or other pages
   - Document any routes without inbound links

### Phase 2: Fix Redirect Chains

1. **Consolidate duplicate/legacy routes**
   - Remove redirect-only routes that point directly to canonical URLs
   - Keep only necessary redirects for backward compatibility

2. **Ensure single canonical path**
   - Add canonical link tags to pages
   - Verify redirect chains are collapsed to 0 or 1 redirect

### Phase 3: Fix Soft 404s

1. **Make missing routes return proper 404**
   - Ensure all unmatched routes return 404 status
   - Verify 404 page is indexable and crawlable

2. **Keep SPA fallback only for authenticated routes**
   - Check which routes require authentication
   - Ensure unauthenticated access to those routes shows proper error

### Phase 4: Link Orphaned Pages

1. **Add discovery paths**
   - Add links from landing page to key content pages
   - Update sitemap if needed

2. **Verify sitemap coverage**
   - Check that all indexable routes are in sitemap
   - Ensure no orphaned indexable pages exist

### Phase 5: Tests

1. **Canonical URL tests**
   - Verify no URL requires >1 redirect
   - Check canonical link tags are present

2. **404 behavior tests**
   - Test missing routes return 404
   - Verify soft 404s are eliminated

3. **Discovery path tests**
   - Test routes are reachable from other pages or sitemap
   - Verify no orphaned indexable routes

4. **Authenticated deep-link tests**
   - Test authenticated users can access deep links
   - Verify unauthenticated access to protected routes shows proper error

## Files to Modify

1. `frontend/src/App.tsx` - Main routing configuration
2. `frontend/src/router.tsx` - Router definitions
3. `frontend/src/pages/` - Page components (404, landing, etc.)
4. `frontend/src/query/` - Query keys for routes
5. `frontend/public/sitemap.xml` - Sitemap generation (if exists)
6. `frontend/src/test/` - E2E tests for route behavior

## Rollback Strategy

If issues arise:

1. Revert frontend routing changes
2. Restore previous redirect behavior
3. Revert 404 handling changes
4. Re-link any orphaned pages
