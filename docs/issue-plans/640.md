## 7. Coupling measurement (evidence)

The measurement tool classifies each commit by which directories it touches. The classifications and current snapshot (last 6 months, 1461 commits, last 3 months, 865 commits, last 12 months, 2383 commits):

- ~5–8% of commits touch BOTH `frontend/` and `app/`+`api/`+`comic_pile/`.
- ~10–12% of commits touch backend only.
- ~28–40% of commits touch frontend only.
- ~25–27% of commits touch infra/CI (`.github/`, `Makefile`, `pyproject.toml`, `package.json`, `pnpm-lock.yaml`, `uv.lock`, `alembic/`, `scripts/`, `tests/`, `tests_e2e/`, `static/`).
- ~5–8% of commits are docs-only.

These numbers are captured by `scripts/coupling_metrics.py` and rendered into a Markdown summary inside the decision document.

## 8. Cross-cutting complexity comparison

The decision document includes a matrix comparing the three options across:

- **CI duplication:** extra workflow files per repo, separate test gates, more reviewers per change.
- **Release coordination:** how a frontend and backend change ship together (single PR vs. coordinated PRs across two repos).
- **Rollback complexity:** can a frontend revert land without re-deploying the API?
- **Observability:** whether logs/metrics/traces stay unified when the runtime is split.
- **Local development:** two `git clone`s, two dev servers, two package managers, two OpenAPI schema hand-offs.
- **Contract management:** is the OpenAPI schema a published artifact, and how often does it drift?
- **Factory execution:** does splitting the repo help or hurt the autonomous factory's claim-lease model?
- **Authentication and security:** does the existing `app/config.py` async-only PostgreSQL rule, the CSRF contract, and the canonical auth recovery flow remain simple across the boundary?

Option 2 (split repos around a published OpenAPI contract) is rejected because (a) only ~5–8% of commits cross the boundary, so the coordination cost dominates the value, (b) the OpenAPI schema is currently refreshed by `scripts/generate_openapi_types.py` in the same repo so a split would require a separate published-package step, and (c) the Vercel single-static-frontend/API-function deployment model only has two paths (`/` → static, `/api/*` → FastAPI), so there is no per-route artifact duplication to justify a repository split.

Option 1 (cleaned monorepo) and Option 3 (single repo, stricter boundaries) are both viable. The decision picks **Option 3** because the prerequisite work has already moved a large fraction of the codebase toward stricter ownership and bounded contracts (generated OpenAPI types, bounded Roll bootstrap, bounded blocked/snoozed summaries, bounded prefetch) and there is no measurable benefit to splitting the repository to gain what the in-repo cleanup has already delivered.

## 9. Trigger for re-evaluation

The decision documents a measurable trigger so the team can revisit the boundary later. The trigger is: when more than 25% of commits in a rolling 90-day window touch BOTH `frontend/` and `app/`+`api/`+`comic_pile/` directly, or when the factory needs a published OpenAPI package to support a new consumer. Until either trigger fires, the single-repo boundary stands.
