# Issue #3220: DB scale 04 - Add Shared Catalog Identity Tables and Nullable Reader-Library Links

## Problem Statement

Issue currently combines a comic identity with a reader-owned progress row. Add a shared identity boundary without replacing any existing personal IDs or duplicating the already-shared provider metadata.

## Scope and Fixed Contract

Implement an additive v1 catalog in one schema/model/repository PR:
- `catalog_series` and `catalog_issues` with BIGINT primary keys
- Each has one required unique `canonical_external_identity_id` FK to existing `external_identities` (RESTRICT deletion)
- `CatalogIssue` may have a nullable `catalog_series_id` until a confirmed series identity is available
- Add nullable indexed `catalog_series_id` to threads and `catalog_issue_id` to issues, with SET NULL on catalog deletion and no changes to personal PKs
- Existing `ExternalIdentity(provider, entity_type, external_id)` remains the identity authority and metadata store; do not copy raw provider JSON into catalog tables
- Series/issue identity type and confirmed-status validation live in the catalog service
- Concurrency-safe get-or-create is keyed by exact confirmed external identity; never by display title, issue number or volume year
- No alias/cross-provider auto-merging in v1
- Unknown/custom entries get no shared catalog row until identity is verified
- Shared catalog is not a public write API and contains no personal fields
- Preserve same-reader canonical identity behavior

## Acceptance Criteria

1. Two different users can reference one CatalogIssue while retaining distinct existing Issue IDs, read states, notes and ratings
2. Unique provider identity under concurrent creation produces one catalog row; incompatible entity types are rejected and conflicts do not overwrite identity
3. New columns are nullable and existing libraries work without a backfill or catalog service calls
4. A catalog issue can exist before its series is resolved; filling a verified series link is additive and never rewrites reader ownership
5. The Alembic migration does not scan/backfill all personal rows, delete data, or run provider network calls; local populated upgrade and downgrade tests pass
6. Document invariants, confirmed-only rules, lock behavior and application rollback in docs/issue-plans/3220.md plus a durable catalog contract document

## Invariants and Contracts

### Catalog Identity Invariants
1. **Canonical External Identity Authority**: `ExternalIdentity(provider, entity_type, external_id)` remains the single source of truth for provider identity and metadata. Catalog tables only reference it.
2. **Confirmed-Only Creation**: Only external identities with `confirmed` status mappings can create catalog entries. Candidate/unresolved/rejected identities are not eligible.
3. **Entity Type Consistency**: `CatalogSeries` must reference an `ExternalIdentity` with `entity_type='series'`. `CatalogIssue` must reference `entity_type='issue'`.
4. **Unique Catalog Entry Per External Identity**: One `ExternalIdentity` → at most one `CatalogSeries` or `CatalogIssue`. Enforced by unique constraint on `canonical_external_identity_id`.
5. **No Cross-Provider Merging**: v1 does not merge identities across providers. Each provider identity gets its own catalog row.
6. **No Title/Number-Based Matching**: Catalog creation is keyed only by exact confirmed external identity (provider, entity_type, external_id).

### Lock Behavior
- **Get-or-Create Concurrency**: Uses PostgreSQL `ON CONFLICT DO NOTHING` with unique constraint on `canonical_external_identity_id`, followed by `SELECT FOR UPDATE` pattern to handle race conditions.
- **Series Linking**: `link_catalog_issue_to_series` uses `UPDATE ... WHERE catalog_series_id IS NULL` to ensure additive-only linking (never overwrites existing link).

### Application Rollback
- Migration is purely additive (new tables, nullable columns)
- Downgrade drops new columns and tables in reverse order
- No data migration means rollback is safe and instant
- Existing `external_identities`, `issues`, `threads` tables unchanged
