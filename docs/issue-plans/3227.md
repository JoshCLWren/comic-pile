# Issue #3227 — DB scale 11: sparse internal queue order keys with dense API positions

Plan version: 2. Frozen contract per the #3227 issue body. Depends on #3217, #3226.

## Problem

Dense `queue_position` updates amplify writes for long queues. Every insert-at-front,
reposition, and completion path rewrites each row whose dense rank moved, so a 10,000-entry
library pays thousands of row updates for a single user action. Ordering authority must move
to a sparse internal key; `queue_position` must stop being the ordering authority.

## Current flow (verified on `main` at the #3227 branch base)

`threads.queue_position` is simultaneously the ordering authority, the pagination key, and
the user-visible position. One column serves all three roles:

- **Ordering.** Every reader sorts with `ORDER BY queue_position[, id]`:
  `app/services/queue_pagination.py::build_sort_order`, `app/repositories/roll_v2_projection.py`
  (bounded candidate CTE and the outer select), `app/repositories/roll_repository.py`
  (bootstrap pool, blocked, library), `comic_pile/queue.py` (`get_roll_pool`,
  `get_roll_pool_rows`, `move_to_safe_position`, `shuffle_queue`),
  `app/repositories/thread_repository.py::fetch_active_threads`,
  `app/repositories/creator_detail.py`, `comic_pile/comicvine_hydrator.py`.
- **Pagination.** `app/services/queue_pagination.py::build_cursor_filter` and
  `build_cursor_values_from_row` key the opaque cursor on `(is_blocked, queue_position, id)`.
- **Displayed position.** `queue_position` is copied straight off the ORM instance into
  `ThreadResponse`, `RollResponse`, `SessionResponse`, `ActiveThreadInfo`, and the persisted
  `selected_queue_position` in `RecommendationContext` (see `app/services/thread_service.py`,
  `app/services/rate_service.py`, `app/services/session_response.py`, `app/api/session.py`,
  `app/api/roll.py`, `app/services/roll_service.py`, `app/services/snooze_service.py`).
- **Write amplification.** `comic_pile/queue.py::_MOVE_POSITION_SQL` and `_MOVE_TO_BACK_SQL`
  renumber the whole reader queue through `row_number()`; `shift_active_queue_positions` and
  the `queue_position + 1` front-insert statements in `app/services/thread_service.py`,
  `app/services/issue.py`, `app/services/provider_issue_adoption.py`, and
  `app/services/thread_state_repair.py` rewrite every active row.
- **Undo/restore.** `app/repositories/undo_snapshot_repository.py` restores ordering through
  `update_thread_queue_positions`, `create_thread_from_state`, and `update_thread_from_state`.

`acquire_queue_lock` already serializes all queue mutations per reader with
`pg_advisory_xact_lock(ADVISORY_LOCK_NAMESPACE, user_id)`. That lock is the correct place to
scope key allocation and rebalance; no new lock is required.

## Fixed decisions

- `ORDER_KEY_SCALE = 1_048_576`. Backfill and rebalance write `rank * ORDER_KEY_SCALE`.
- Authoritative ordering expression is
  `COALESCE(queue_order_key, queue_position * ORDER_KEY_SCALE)`, always with `id` as the
  deterministic tie-break. The legacy arm makes the pre-backfill and post-backfill orders
  numerically identical, so ordering never changes when keys are populated.
- `Issue.position` is untouched. The key is queue-only.
- Positional reorder input stays 1-based and dense: `move_to_position` keeps translating the
  requested dense position into a `(previous_key, next_key)` pair for the reader.
- Key allocation and rebalance are scoped per reader under the existing advisory lock, inside
  the caller's transaction, so they are rollback-safe with the rest of the mutation.

## Acceptance-criterion conflict found while planning

Criterion 2 ("a common single move in 10,000 active entries updates O(1) order rows") and the
repository's existing required suite are only simultaneously satisfiable if `queue_position`
stops being a stored dense column.

`tests/test_queue_position_perf.py` pins the stored column, not the API projection:

- `test_concurrent_repositioning_no_duplicate_positions` asserts
  `positions == list(range(1, 21))` after ten concurrent moves.
- `test_move_to_position_*` and `test_cross_user_isolation` assert dense `[1, 2, 3, 4]` /
  `[1, 2, 3, 4, 5]` collections read directly from `threads.queue_position`.

Roughly 210 files under `tests/` reference `queue_position`. Consequently the cutover cannot be
landed as a small delta on top of the current schema-only PR: `queue_position` has to become a
read-time dense projection (`row_number() OVER (ORDER BY <order expr>, id)`) and the suites
that pin the stored column have to be migrated in the same coherent change. This is the scope
the current PR head does not yet deliver.

## Implementation steps

1. **Ordering helpers.** New `app/repositories/queue_order.py` owning `ORDER_KEY_SCALE`,
   `order_key_expression()`, `order_by_clause()`, `dense_position_window()`, midpoint
   allocation, and the `needs_rebalance` predicate. Repositories own all SQL for the
   `Thread` family; `comic_pile.queue` composes these helpers for the existing raw-SQL move
   statements so no service builds SQL.
2. **Write paths become O(1).** `move_to_position`, `move_to_front`, `move_to_back`,
   `move_to_safe_position`, `shuffle_queue`, `shift_active_queue_positions`, the
   `queue_position + 1` front-insert statements, and every `max_queue_position + 1` append
   write a sparse key for the affected rows only. `comic_pile/queue.py` returns changed
   `queue_order_key` values alongside changed positions so callers keep their delta maps.
3. **Rebalance.** When no integer midpoint remains between two neighbours, renumber that
   reader's active queue to `rank * ORDER_KEY_SCALE` inside the same transaction, under the
   existing advisory lock. Bounded, deterministic, and rolled back with the mutation.
4. **Dense projections.** `fetch_queue_page`, `fetch_completed_page`, `fetch_excluded_page`,
   `fetch_active_threads`, `queue_repository.active_queue_positions`,
   `roll_v2_projection`, `roll_repository`, `creator_detail`, `admin_service`,
   `comicvine_hydrator`, and `queue.get_roll_pool*` select the dense window and order by the
   key expression. Keyset cursors carry the order key rather than the dense position, so page
   boundaries stay stable under concurrent moves.
5. **Undo/restore.** `undo_snapshot_repository.update_thread_queue_positions`,
   `create_thread_from_state`, and `update_thread_from_state` capture and restore
   `queue_order_key`; `undo_snapshot_service` records the key in the delta so undo reproduces
   the exact prior order instead of a stale dense cache.
6. **Backfill.** Bounded-batch backfill ordered by `(user_id, rank)`, run as a service, with
   the `COALESCE` fallback above covering every row the backfill has not reached yet. Backfill
   is resumable and idempotent.
7. **Indexes.** `ix_thread_user_active_queue_position (user_id, is_blocked, queue_position, id)
   WHERE status = 'active'` and `ix_thread_user_status_position (user_id, status,
   queue_position)` cannot serve `ORDER BY COALESCE(queue_order_key, queue_position * N)` once
   keys are populated. Replace them with expression indexes on the order expression in the
   same migration that enables key-ordered reads, and only then drop the order-containing
   btree indexes, per the issue's "no order-containing index without demonstrated need".

## API contract

No wire change. `queue_position` stays a 1-based dense integer in every response, cursor, and
export. Only the storage authority moves. Cursors remain opaque base64 tokens; the payload
shape is unchanged, and the encoded sort value becomes the authoritative order key so a
concurrent insert cannot move a later page behind an earlier one.

## Authorization changes

None. Every read and write remains scoped by the existing `Thread.user_id == current_user.id`
predicate.

## Migration and rollback

`p322700000001` adds `threads.queue_order_key BIGINT NULL` and is inert until keys are
written, so it is safe to deploy ahead of the cutover and safe to leave in place during the
compatibility window. `downgrade` drops the column; because every reader falls back to
`queue_position`, a downgrade before the btree indexes are dropped loses no durable state.
Rollback order is: stop writing keys, restore dense `queue_position` from the order
expression, drop the expression indexes, then downgrade the column. The order-containing
btree indexes are dropped last and only after the replacement expression indexes are serving
production reads, so a rollback never leaves the queue table unindexed.
