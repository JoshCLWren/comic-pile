# Issue #4254: Option E migration parity - Planetary / Authority Plan #29

## Problem Statement

Planetary / Authority Plan #29 lacked a durable owned-List source. The
read-only production census on 2026-10-27 observed:

- Reading List #1000018 (`user_id=1`): `Planetary / Authority`, `strict`,
  145 unique issues, first unread/unskipped at zero-based position 14.
- Reading Plan #29 (`user_id=1`): `Planetary / Authority`,
  `strict_sequential`, 144 unique issues. Its only source was
  `comicvine:4050-18250` (`reading_plan_sources` #1000049,
  `custom_cbl_list_id = NULL`).
- Membership overlap 144/145. List position 32 (Issue #1119158) was missing
  from the Plan; the first four positions (26500, 26520, 26525, 26496) were
  ordered differently. After accounting for those, plan/list order was aligned.
- Read/unread state lives on the List. The obsolete Plan edit route fell back
  to `/continuity-plans/29/edit` because no owned `custom-cbl:<id>` source
  existed. PR #4253 added a read-only ownership fallback; it is not a data
  migration.

## Root Cause

The Option E cutover made an owned Reading List the single issue-order
authority, but the conversion backfill had not yet written the explicit
`custom-cbl:1000018` source for the audited `(user, plan) -> list` identity.
Without that link the Plan reader could only fall back to historical Plan
rows, so the List-only Issue and List ordering were invisible.

## Repair Status

### Audit and durable source (complete)

Migration `c42550000001_complete_option_e_source_links.py` backfills the
missing durable link. For the audited identity `(user_id=1, plan_id=29)` it:

- verifies the target List is owner-scoped, `strict`, and still has the audited
  144/145/144 overlap before writing anything;
- inserts `custom-cbl:1000018` into `reading_plan_sources` while retaining the
  existing `comicvine:4050-18250` provenance row;
- never copies List membership or order into `reading_plan_issues`;
- ends with a post-check that fails the migration unless every Plan resolves to
  exactly one owner-scoped List, so no Plan is left with a missing durable
  link.

`scripts/report_custom_cbl_plan_reconciliation.py` is the repeatable read-only
census for plan/list membership, order drift, durable link IDs, the first
unread/unskipped frontier, source links, and provenance. It never writes and
never infers authority from names.

### Reconciliation decision: the List is authoritative (complete)

The missing Issue and early ordering variation are **not** repaired by editing
historical Plan rows or the owner's List. In Option E,
`app/services/reading_plan_reader.py::_project_authoritative_list` projects the
linked List for every issue and position, so the Plan reader already serves:

- all 145 List entries, including Issue #1119158 at List position 32;
- the early four entries in List order, not stale Plan order;
- the List's first-unread frontier at position 14;
- the linked `custom-cbl:<id>` source, which
  `frontend/src/pages/ReadingPlanEditRoute.tsx` uses to route editing to
  `/reading-lists/1000018`.

Historical `reading_plan_issues` rows stay at 144 as retained provenance. No
production data mutation is required or authorized by this issue.

### Roll eligibility is unchanged by the durable source (complete)

Roll/Queue candidate selection never reads the durable Plan-to-List source.
`app/services/reading_eligibility_service.py::load_eligibility_snapshot`
builds its snapshot through `app/repositories/reading_shadow_repository.py::load_shadow_inputs`,
which selects only owner-scoped Threads, Issues, Reading Lists, List entries,
collection exclusions, overlap decisions, and reader-authored prerequisites.
Neither `continuity_plans`, `reading_plan_issues`, `reading_plan_sources`,
`reading_plan_source_placements`, nor `reading_plan_dependencies` participates, so
writing `custom-cbl:1000018` cannot add, remove, or reorder a Roll candidate.
`reading_plan_source_placements` is left untouched by the migration and is
reported by the census.

### Regression evidence (complete)
