# DB Scale 09: Enforce Reader Ownership Consistency - Planning Document

## Scope

This issue requires planning to enforce reader ownership consistency at graph and library write boundaries in Comic Pile.

### Problem

Foreign keys ensure referenced IDs exist, but many relationships depend on application validation to prove consistent ownership. Shared catalog IDs must not weaken that boundary.

### Acceptance Criteria

- [ ] Cross-user graph/member/pending/frontier writes are rejected through APIs and central service paths even when both users share one CatalogIssue
- [ ] A next_unread_issue_id belonging to a different Thread of the same reader is rejected
- [ ] Chosen DB-enforced relationships reject invalid direct SQL inserts; application-only/polymorphic boundaries have explicit rejection tests and documented scope
- [ ] Preflight reports existing invalid rows without private payloads; migrations preserve all valid history and do not auto-repair ambiguous ownership
- [ ] Read-only shared catalog access does not grant access to personal notes, corrections, tags, events or read state

### Planning Status

This document represents the planning phase for issue #3225. The implementation has not yet been completed.

### Implementation Plan (Proposed)

Upon completion of planning, the following implementation approach is proposed:

#### 1. Database Constraints

Add ownership constraints to enforce reader consistency:

**Thread.next_unread_issue_id**:
- Add composite FK to ensure next_unread_issue_id belongs to the same thread's user
- Add trigger or CHECK constraint to validate ownership

**ReadingSession.pending_thread_id**:
- Add FK to ensure pending_thread_id belongs to the session's user
- Add FK to ensure pending_thread_id's thread has issues

**ReadingSession.pending_issue_id**:
- Add FK to ensure pending_issue_id belongs to the same thread as pending_thread_id
- Add FK to ensure pending_issue_id's thread belongs to the session's user

**ReadingPlanIssue**:
- Add FK to ensure plan_id belongs to the same user as the issue's thread
- Add FK to ensure issue_id belongs to a thread owned by the plan's user

**ReadingPlanDependency**:
- Add FK to ensure plan_id belongs to the same user as the dependency's issues
- Add FK to ensure dependency_id's issues belong to the plan's user

**TagAssignment**:
- Add FK to ensure tag_id's owner matches the assignment's target owner (for private tags)
- Add FK to ensure target belongs to the same user as the tag owner (for private tags)

#### 2. Service/Repository Validation

Add validation functions in services and repositories:

**ThreadService**:
- `validate_next_unread_issue(thread_id: int, issue_id: int, user_id: int) -> bool`
- Ensure issue belongs to the same thread and thread belongs to the user

**ReadingSessionService**:
- `validate_pending_thread(session_id: int, thread_id: int, user_id: int) -> bool`
- Ensure thread belongs to the user
- Ensure thread has issues

- `validate_pending_issue(session_id: int, issue_id: int, user_id: int) -> bool`
- Ensure issue belongs to a thread owned by the user
- Ensure issue belongs to the same thread as pending_thread_id if set

**ReadingPlanService**:
- `validate_plan_issue(plan_id: int, issue_id: int, user_id: int) -> bool`
- Ensure plan belongs to the user
- Ensure issue belongs to a thread owned by the user

- `validate_plan_dependency(plan_id: int, dependency_id: int, user_id: int) -> bool`
- Ensure plan belongs to the user
- Ensure dependency's issues belong to the user

**TagService**:
- `validate_tag_assignment(tag_id: int, target_type: str, target_id: int, user_id: int) -> bool`
- Ensure tag and target belong to the same user (for private tags)
- Ensure target exists and belongs to the tag owner (for private tags)

#### 3. Tests

Add comprehensive tests for ownership validation:

- Test cross-user writes are rejected
- Test same-user wrong-thread frontier is rejected
- Test DB-enforced constraints reject invalid inserts
- Test preflight reports existing invalid rows
- Test read-only shared catalog access does not grant access to personal data

#### 4. Migration

Create Alembic migration to add constraints without breaking existing data:
- Use `ON CONFLICT DO NOTHING` for constraint violations
- Run preflight to identify and report violations
- Do not auto-repair ambiguous ownership
