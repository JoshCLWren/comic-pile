# DB Scale 09: Enforce Reader Ownership Consistency - Implementation Plan and Evidence

## Scope

Issue #3225. Reader ownership is an enforced property of every graph and
library write boundary instead of an application convention. Shared catalog
identity (`catalog_issues`, #3220) is a shared reference, never authorization
evidence.

The canonical boundary contract lives in
[`docs/READER_OWNERSHIP_CONSISTENCY.md`](../READER_OWNERSHIP_CONSISTENCY.md).
This document records the delivered scope and the acceptance evidence.

## Problem

Foreign keys ensure referenced IDs exist, but many relationships depend on
application validation to prove consistent ownership. Shared catalog IDs must
not weaken that boundary.

## Acceptance Criteria

- [x] Cross-user graph/member/pending/frontier writes are rejected through APIs
  and central service paths even when both users share one `CatalogIssue`.
- [x] A `next_unread_issue_id` belonging to a different `Thread` of the same
  reader is rejected.
- [x] Chosen DB-enforced relationships reject invalid direct SQL inserts;
  application-only/polymorphic boundaries have explicit rejection tests and
  documented scope.
- [x] Preflight reports existing invalid rows without private payloads;
  migrations preserve all valid history and do not auto-repair ambiguous
  ownership.
- [x] Read-only shared catalog access does not grant access to personal notes,
  corrections, tags, events or read state.

## What was delivered

### 1. Database enforcement (`app/ownership_constraints.py`)

Two PostgreSQL triggers installed by migration `m5d400000001` and by
`Base.metadata.create_all` (so the test fixtures exercise exactly the
production schema):

- `trg_threads_frontier_ownership` - `threads.next_unread_issue_id` must
  reference an issue of that exact thread.
- `trg_sessions_pending_ownership` - `sessions.pending_thread_id` must reference
  a thread owned by the session's reader.

Both reject invalid direct SQL inserts and updates with
`integrity_constraint_violation`. The existing single-column foreign keys and
their `ON DELETE SET NULL` behaviour are unchanged, so no delete path changes.
The rationale for triggers over composite foreign keys is documented in
`docs/READER_OWNERSHIP_CONSISTENCY.md`.

### 2. Centralized service validation

`app/services/ownership_consistency.py` is the single typed validator; the SQL
lives in `app/repositories/ownership_consistency_repository.py`.

- `ensure_thread_frontier_issue` - wired into `thread_service.set_current_issue`.
- `ensure_pending_thread_owned` - wired into `thread_service.set_current_issue`.
- `ensure_issue_ids_owned` - wired into plan membership below.
- `reader_ownership_violation_report` - the payload-free preflight report.

`reading_plan_normalization.rebuild_plan_membership` now calls
`ensure_plan_issue_membership_owned` before any row is replaced, so every plan
membership write path (API, CBL adoption, migration, repair script) rejects
issues the plan's reader does not own. A missing issue and another reader's
issue produce the identical 422 `unowned_plan_issue`, so the boundary is not an
existence oracle.

Dependency endpoints (`create_dependency`), plan dependency membership
(`link_dependency_to_plan`), and polymorphic tag assignments
(`tag_service`) already resolved ownership at their central write paths and are
now covered by explicit rejection tests rather than reimplemented.

### 3. Read-only preflight

- `scripts/audit_reader_ownership_violations.py` - repeatable read-only report;
  counts plus bounded primary-key lists only; exits `1` on any violation.
- `alembic/preflight/m5d400000001.json` - the same detection as a machine
  enforced, read-only production preflight before `alembic upgrade head`.

Neither deletes, remaps, nor auto-repairs a row.

## Verification

`tests/test_reader_ownership_consistency.py` covers:

- direct SQL cannot point a frontier at another thread's issue (same reader) or
  another reader's issue, and cannot smuggle a foreign frontier through a raw
  `INSERT INTO threads`;
- direct SQL cannot point a reading session at another reader's thread, nor
  smuggle one through a raw `INSERT INTO sessions`;
- the reader's own frontier/pending references are accepted, and deleting a
  frontier issue still clears the reference through the existing
  `ON DELETE SET NULL` path;
- two readers whose issues share one `CatalogIssue` cannot adopt each other's
  issue, and the private tag/note payload never enters the preflight report;
- plan membership rejects another reader's issue and a missing issue with the
  same 422, accepts the plan reader's own issue, and is a no-op for plans with
  no issue nodes;
- the preflight manifest is valid, read-only, and selects no reader payload;
- the migration installs byte-identical trigger DDL to `create_all`.

## Frozen boundaries honored

- The PostgreSQL schema is evolved in place; existing `User`/`Thread`/`Issue`/
  `Event` ids, wire contracts, history, personal notes, ratings, queue intent,
  and plan/provenance links are untouched. The migration adds triggers only: no
  column, table, or row is added, altered, or removed.
- No row is deleted or silently remapped.
- No Row Level Security and no new auth-session model.
- No production mutation: the audit script is read-only and only runs when
  explicitly pointed at a database.
