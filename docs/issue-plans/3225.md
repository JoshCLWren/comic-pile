# Issue #3225: DB scale 09 — enforce reader ownership consistency at graph and library write boundaries

Plan version: 1. Frozen contract per issue body. Depends on #3220 (closed).

## Problem

Foreign keys prove referenced IDs exist, but most reader-ownership edges
(issue→thread→user, dependency endpoints, plan membership, session pending
pointers, tag assignments) rely on application validation. Shared
`catalog_issues` / `catalog_series` rows (issue #3220) must never become
authorization evidence: two readers may reference one `CatalogIssue` while
their personal `Issue` rows, notes, ratings, tags, events, and read state
stay strictly per-reader.

## Write-path inventory (supported paths hardened by this slice)

| # | Write path | Owner check (before → after) | Enforcement |
|---|---|---|---|
| 1 | Issue-to-Thread (`POST /threads/{id}/issues`, adoption, reorder/move) | `get_owned_thread_or_404` already scopes the parent thread; kept, plus catalog-is-not-auth comment | application (central guard documents it) |
| 2 | `Thread.next_unread_issue_id` (`set_current_issue`, migrate/reactivate/rate/mark flows) | user-controlled entry (`set_current_issue`) gains explicit `require_frontier_in_thread`; derived flows already select from same-thread queries | NEW composite FK `fk_threads_frontier_same_thread` + guard |
| 3 | Dependency endpoints (`POST /dependencies/`, note update, delete, batch readers) | `create_dependency` already requires both endpoint threads owned; centralized into `ownership_guard.require_dependency_endpoints_owned` | application (join-through-thread) |
| 4 | Plan-to-Issue membership (`rebuild_plan_membership` via canonical writer) | `validate_node_ownership` already 422s dangling refs; issue-node check centralized into guard | application |
| 5 | Plan-to-Dependency links (`link_dependency_to_plan`) | already requires both edge endpoints owned; centralized into guard | application |
| 6 | `ReadingSession` pending refs (`set_pending_thread`, `set_current_issue`, rate/snooze clear) | NEW `require_session_pending_consistent`: pending thread/item owned by session owner, pending issue in pending thread | application |
| 7 | Tag assignments (single + bulk, assign/unassign) | `_validate_target` already enforces private-tag ownership via explicit owner query; owner resolution centralized into `ownership_guard.target_owner_id` | application (polymorphic: FK unavailable) |

Read-only shared-catalog access (`search_catalog_*`, projections) is unchanged
and grants no personal data: catalog rows carry no notes, ratings, tags,
events, or read state.

## Why only the frontier gets a DB constraint

- `fk_threads_frontier_same_thread`: `threads(id, next_unread_issue_id)`
  references `issues(thread_id, id)` (backed by new `uq_issues_thread_id_id`).
  `DEFERRABLE INITIALLY DEFERRED` so same-transaction frontier recomputation
  (e.g. single-issue delete moves the pointer then deletes the row) commits
  atomically. `NULL` frontiers pass. This is an ordinary composite FK, needs
  no catalog duplication, and changes no wire IDs.
- Cross-user edges stay application-enforced: `issues` and `dependencies`
  carry no `user_id` (ownership lives on `threads.user_id`), and denormalizing
  it would duplicate the single thread→user authority and risk divergence.
  `tag_assignments(target_type, target_id)` is polymorphic with no single FK
  target, so centralized typed validation (`ownership_guard.target_owner_id`)
  is the enforcement point. Catalog FKs (`catalog_issue_id`,
  `catalog_series_id`) are deliberately excluded from every ownership check:
  shared identity must never authorize access to another reader's rows.

## Read-only preflight (before constraints)

`scripts/check_ownership_consistency.py` (asyncpg, `SET TRANSACTION READ
ONLY`, 5s statement timeout) reports per-category **counts and IDs only** —
no titles, notes, ratings, payloads, or credentials:

- frontier mismatches (`threads.next_unread_issue_id` pointing outside the thread)
- cross-user dependency endpoints (either endpoint's thread owned by another user)
- plan-issue / plan-dependency cross-user rows (member/edge owner ≠ plan owner)
- session pending cross-user or pending-issue-not-in-pending-thread rows
- private-tag assignments whose target is owned by another user

The migration refuses to install the frontier constraint while any frontier
violation exists (fail/report, never delete or silently remap). All other
categories are reported for triage; existing valid history is preserved and
ambiguous rows are never auto-repaired.

## Implementation steps

1. `app/services/ownership_guard.py` (new): `OwnershipError` domain error,
   `require_*` validators raising the caller's existing HTTP semantics
   (404 owned-or-not-found, 422 `dangling_plan_reference`), `target_owner_id`
   for polymorphic targets, `detect_violations` returning counts + IDs only.
2. Wire guards into `dependency_service.create_dependency`,
   `thread_service.set_current_issue` (+ pending consistency in
   `set_pending_thread`/`set_current_issue`), `continuity_plan_writer`
   issue-node validation, `reading_plan_normalization.link_dependency_to_plan`,
   `tag_service._validate_target` owner resolution.
3. Models: `Issue` gains `uq_issues_thread_id_id`; `Thread` gains
   `fk_threads_frontier_same_thread` (`use_alter=True`, deferrable deferred).
4. Migration `p322500000001_frontier_same_thread_fk` (child of `c36630000001`):
   preflight frontier check → add unique + FK → downgrade drops both.
5. `scripts/check_ownership_consistency.py` + `tests/test_reader_ownership_consistency_3225.py`:
   cross-user shared-catalog attacks (dependency, plan member, plan link,
   session pending, private tag), same-user wrong-thread frontier rejection
   (service + direct-SQL FK violation), preflight redaction (no titles/notes).
6. Docs: this plan + `docs/READING_GRAPH_ADR.md` addendum section on the
   ownership boundary (or a short durable note if ADR append is out of scope).

## Risks / frozen boundaries

- No RLS, no new auth-session model, no Thread.format resurrection (#3035),
  no creator-entry UX duplication (#3145), no reread/copy semantics, no
  title/number auto-matching, no production mutation.
- `Issues.thread_id` ON DELETE CASCADE and column `next_unread_issue_id`
  ON DELETE SET NULL semantics are unchanged; the composite FK is
  `NO ACTION ... DEFERRABLE INITIALLY DEFERRED` so it never nulls a PK and
  never blocks cascade deletes of whole threads.
- Single-issue delete recomputes the frontier before commit (`delete_issue`
  → `apply_thread_issue_tracking_state`); the deferred check sees only the
  final state.
- Catalog links remain nullable `SET NULL`; this slice adds no backfill.

## Rollback

- Code: revert guard call-sites to prior inline checks (identical semantics).
- Migration downgrade drops `fk_threads_frontier_same_thread` and
  `uq_issues_thread_id_id`; application validation continues to reject bad
  writes. No data migration means rollback is instant and lossless.
