## MANDATORY: API version is not an implementation language (Rust cutover #4335)

The `v1`, `v2`, etc. segments in public HTTP paths refer **only to API contract versions**, not Python, Rust, a new server, or a migration phase. Both Python and Rust can implement any API version. Never describe an operation as "Python v1" or "Rust v2" without explicitly distinguishing the exact path from its **observed/current** runtime.

**A Rust cutover replaces the implementation behind the same HTTP method, URL and aliases.** First trace the live frontend/background/recovery callers to that precise path, its existing handler, its generated OpenAPI operation and its actual PostgreSQL statements and transaction behavior. Keep the client's URL and wire contract unchanged; never redirect `/api/v1/...` to `/api/v2/...` as a shortcut to reach Rust. Changing API versions is a separate, deliberate API change, not a language replacement.

Before changing an operation, trace the exact HTTP method and path, its current
ingress destination and observed runtime, generated contract, real callers, and
PostgreSQL/transaction behavior. Keep the URL and wire contract unchanged unless
a separate API-version decision explicitly changes them. Verify same-path
behavior with focused tests and, for a deployed runtime change, a successful
real authenticated production request. Do not infer runtime from a URL version
or claim migration from an unused parallel endpoint. Coordinate with active
factory claims and do not bundle unrelated API refactors.

## Project Overview

Comic Pile is a dice-driven comic reading tracker built with:
- **Backend**: native Rust (`native/roll-service`, axum, `tokio-postgres`), deployed through `api/native_roll.rs`; no Python application code remains
- **Frontend**: React 19, Vite, Tailwind CSS
- **Database**: PostgreSQL, migrated by the Rust refinery runner (`native/migrate`); Alembic is retired
- **Package managers**: `cargo`, `pnpm` (frontend), `uv` (Python tooling scripts and repository checks only)

## Database query efficiency (owner rule, November 15, 2026)

Write efficient PostgreSQL queries by construction. No SQL inside loops over rows, issues, threads, or users; prevent N+1 fetches and per-item round trips. Prefer set-based joins/CTEs, bounded batch requests, indexed filters, predictable pagination, and one coherent transaction where required. Do not materialize whole libraries or introduce screen-level request waterfalls. Preserve ownership checks, authorization, idempotency, locking, and correct snapshot semantics rather than chasing an arbitrary number of statements. If a real slow query or performance regression is demonstrated, profile the actual workload and fix it with a focused test.

**The blanket per-route SQL-budget program is canceled by the owner.** Never require numeric statement ceilings, a `sql_budget` entry, `pg_stat_statements` proof for every endpoint, small/large fixture quotas, or SQL-budget coverage tickets as a prerequisite for a Rust migration. ## API Patterns

### Layering Rule (Native Rust)
Handlers validate and delegate; domain modules decide; persistence stays behind shared DB helpers.

- **Handlers** live in `native/roll-service/src/lib.rs` and per-resource modules (`roll_offer.rs`, `continuity_plans.rs`, ...). They parse and validate the request, apply auth and ownership checks, call domain logic, and map outcomes to HTTP statuses. Handlers must not open ad-hoc connections or hand-roll repeated SQL plumbing.
- **Domain modules** own business rules and transaction boundaries for their resource family.
- **Persistence** uses the bounded pool and SQL helpers in `native/roll-service/src/db.rs`; request/response DTOs derive `serde`/`utoipa` and stay aligned with the generated contract.

New backend code follows this layout without exceptions. Every native route module requires a DB-backed HTTP test; the `native-route-db-test-guard` CI job enforces that with `node scripts/check_native_route_db_tests.mjs`. The former Python router/service/repository layout and its conformance baseline were retired with the Python API.

### Domain Nouns With Multiple Meanings (House Standard)

A domain noun that also names something else must be qualified at every boundary. Never expose a
domain concept to application code under a bare, ambiguous name when a second meaning exists in the
same codebase.

- The durable reading-history model is the Rust `ReadingSession` resource (`native/roll-service/src/reading_session.rs`), backed by the `sessions` table. It is never `Session`, `sessions`, or `SessionModel` in code. <!-- docs-path-check: ignore -->
- Auth state has its own precise names: access token, refresh token, `password_changed_at` (credential epoch), `revoked_tokens`, and `password_reset_tokens`. There is no auth-session persistence model, and none may be added just to make naming symmetrical.
- Auth modules (`native/roll-service/src/auth/`) must not import or call reading-history persistence. Revoke credentials with auth state; reading history is not a credential. <!-- docs-path-check: ignore -->
- Storage/API edges keep the established wire names: the `sessions` table, the `session_id` path parameter in v2 reading-session URLs, and the `SessionDetails`/`SessionSnapshotsResponse` client types. Retrofitted v1 names such as `/api/session/`, `SessionListItem`, or singular `SessionDetail` are retired and must not be presented as current contracts. Ambiguity is resolved in code, not on the wire.
- A password reset must preserve populated reading history; the Rust auth module operates only on auth state.

See [`docs/READING_SESSION_NAMING.md`](docs/READING_SESSION_NAMING.md) for the full convention, the
retained-ambiguity inventory, and the rationale from the #2996 password-reset incident.

### Request and Response DTOs
All API input/output uses Rust structs that derive `Serialize`, `Deserialize` and the
applicable `utoipa::ToSchema` in the resource module:
```rust
#[derive(Debug, Serialize, Deserialize, ToSchema)]
pub struct ThreadCreate {
    pub title: String,
    pub format: String,
    pub issues_remaining: i32,
    pub notes: Option<String>,
}
```
Validate bounded fields explicitly (length, range, checked arithmetic) before use; there is no
Pydantic-style declarative validator layer.

### Database Rows
Table columns are read through `tokio-postgres` in `native/roll-service/src/db.rs` and the
resource modules. Read PostgreSQL `int4` columns as `i32` (or cast `::bigint` in SQL); never
`row.get::<i64>` on an `int4` column.

### Error Handling
Map domain failures to explicit HTTP statuses inside the handler and return a JSON `detail`
body. Ownership failures return `404` rather than confirming another account's resource exists.
```rust
if thread.user_id != current_user.id {
    return Err(ApiError::not_found(format!("Thread {thread_id} not found")));
}
```

## Frontend Code Style

- Functional components with hooks
- **Server state is managed with TanStack React Query (`@tanstack/react-query`)** — never hand-rolled `useState`/`useEffect` fetch hooks. `useQuery` for reads, `useMutation` for writes.
- React Router for navigation

**Query directory layout (`frontend/src/query/`):**

- `queryKeys.ts` — all query-key builders live here. Use hierarchical per-domain namespaces
  (`queue`, `session`, `roll`, `thread`, `dependencies`, `analytics`) with `all`/`list`/`detail`/`page`
  shapes and `as const`. Normalize filter params (e.g. trimmed/nullable search) so keys stay
  canonical. Never inline raw key arrays inside components or hooks.
- `queryClient.ts` — the single shared `QueryClient` with app defaults (`staleTime` 30s, `gcTime`
  5min, `refetchOnWindowFocus: false`, no retry on 401/403-auth, mutations `retry: false`).
- `cacheEffects.ts` — **all** cache writes, invalidation, and optimistic-update helpers live here
  (e.g. `invalidateAfterQueueMutation`, `applyEditedThreadToQueuePages`,
  `optimisticallyUpdateThreadCache`). Keep these centralized rather than scattering
  `setQueryData`/`invalidateQueries` calls through components.

**Query keys naming:** build every key through `queryKeys.*` from `queryKeys.ts`. Prefer stable keys
with normalized params; put pagination cursors in `pageParam`, not in the key.

**Reads (`useQuery`):** wrap a service call from `frontend/src/services/api.ts`; gate with `enabled`; keys from
`queryKeys.*`. Return `{ data, isPending, isError, refetch }`.

**Writes (`useMutation`):** `mutationFn` calls the API service; `onSuccess` performs cache effects
(usually an invalidation/update helper from `cacheEffects.ts`). Return `{ mutate, isPending,
isError }`. The mutation is the single source of truth for the write; do not call `refetch()`
manually after an invalidation helper that already triggers refetch.

**Optimistic updates:** when a mutation should feel instant, call
`optimisticallyUpdateThreadCache(client, id, update)` (or the matching `cacheEffects.ts` helper)
in `onMutate`, keep the returned rollback function, and call it in `onError` to restore the prior
cache. Always pair optimistic writes with a rollback path.

```tsx
import { useQuery, useMutation } from '@tanstack/react-query'
import { threadsApi } from '../services/api'
import type { Thread } from '../types'
import { queryClient } from '../query/queryClient'
import { queryKeys } from '../query/queryKeys'
import {
  invalidateAfterQueueMutation,
  optimisticallyUpdateThreadCache,
} from '../query/cacheEffects'

export function useThread(id?: number | null) {
  return useQuery({
    queryKey: id ? queryKeys.thread.detail(id) : [],
    queryFn: () => threadsApi.get(id!),
    enabled: !!id,
  })
}

export function useRenameThread() {
  return useMutation({
    mutationFn: ({ id, title }: { id: number; title: string }) =>
      threadsApi.update(id, { title }),
    onMutate: async ({ id, title }) => {
      const rollback = optimisticallyUpdateThreadCache(
        queryClient,
        id,
        (thread: Thread) => ({ ...thread, title }),
      )
      return { rollback }
    },
    onError: (_err, _vars, ctx) => ctx?.rollback?.(),
    onSuccess: async () => {
      await invalidateAfterQueueMutation(queryClient)
    },
  })
}

export default function ExamplePage() {
  const { id } = useParams()
  const { data, isPending, isError } = useThread(Number(id))
  const rename = useRenameThread()

  if (isPending) return <div>Loading...</div>
  if (isError) return <div>Error loading thread</div>

  return (
    <div>
      {data?.title}
      <button onClick={() => rename.mutate({ id: Number(id), title: 'New' })}>Rename</button>
    </div>
  )
}
```

**Single place for conventions:** this section is the canonical reference for frontend server-state
conventions. Any query-key, cache-effect, or optimistic-update pattern must match what is implemented
in `frontend/src/query/` (see `queryKeys.ts`, `queryClient.ts`, `cacheEffects.ts`) and the
`frontend/src/hooks/` wrappers.

## Greptile Review Rules

The following rules in `.greptile/config.json` are enforced by Greptile during PR review. These rules cite concrete failure classes from recurring defects:

### High Severity Rules

1. **rust-write-lock-order**: Rust write paths take the per-reader queue advisory lock BEFORE any thread/issue row lock (SELECT ... FOR UPDATE); every new/changed writer needs a concurrent DB test against sibling writers (#5398/#5419 deadlocks).

2. **bounded-input-before-allocation**: Request-supplied counts/ranges must be bounded and use checked arithmetic before allocating, looping or inserting; prefer set-based SQL (generate_series/unnest) (#5398 12GB alloc, #5420 overflow bypass).

3. **python-parity-wire-contract**: Rust replacements of frozen Python routes must match production wire behavior — validation 422 body `{"detail":"Validation failed"}`, always-emitted `[]` / `null` instead of omitted fields, Python round()/int parsing semantics; require golden tests measured from Python (#5428, #5451, #5439, #5411).

4. **postgres-integer-width**: int4 columns read as i32 or cast ::bigint in SQL; never row.get::<i64> on int4 (#5351 panic).

5. **no-test-weakening**: Flag removed/loosened assertions, added timeouts/retries/sleeps, or new skip guards; flaky tests are deleted and redesigned deterministically (owner rule).

6. **bot-owned-route-outputs**: PRs must not change vercel.json, docs/api/v2-route-inventory.json, docs/api/route-fragments/vercel-rewrites.json or the AGENTS.md route-burndown marker block.

### Medium Severity Rules

7. **tests-no-network**: Tests must not call real external services (GitHub, ComicVine); use injectable fakes (#5339).

### No-SQL-in-loops Reference

8. **no-sql-in-loops**: No SQL inside loops over rows, issues, threads, or users; prevent N+1 fetches and per-item round trips. Prefer set-based joins/CTEs, = ANY($1) / unnest batched statements, bounded batch requests, indexed filters, and predictable pagination. See AGENTS.md Database query efficiency rule.
